## 1. Natural-language intent and command routing

Ollama supports supplying a JSON schema to constrain output, including schemas generated from Pydantic models. Shape constraints help produce parseable classifications but do not establish that an intent or target is semantically correct. [Ollama structured outputs](https://docs.ollama.com/capabilities/structured-outputs)

Decision: exact slash commands and active approval/cancellation input take precedence. Ordinary language then enters a bounded classifier returning intent, target, confidence, and reason, validated with existing Pydantic machinery. Deterministic authorization derives from the requested operation and opened workspace; a classifier cannot grant privileges. Low-confidence input should request the smallest missing choice while retaining the draft. Distinguish conversation, inspection, learning, implementation, and self-work without requiring special phrases. Keep an offline deterministic fallback and log which route actually ran.

Acceptance: paraphrase corpus, negation, quoted instructions, ordinary mention of Xander versus a request to edit Xander, Unicode, unknown targets, malformed classifier output, and unavailable backend.

## 2. Web research and crawling

Crawl4AI supplies extraction, cache control, browser execution, and bounded deep crawling. Context7 confirms `CrawlerRunConfig(check_robots_txt=True, page_timeout=...)` and `BFSDeepCrawlStrategy(max_depth=..., max_pages=..., include_external=...)`; the page cap otherwise defaults to unbounded. [Crawl4AI deep crawling](https://github.com/unclecode/crawl4ai/blob/main/docs/md_v2/core/deep-crawling.md), [SDK reference](https://github.com/unclecode/crawl4ai/blob/main/docs/md_v2/complete-sdk-reference.md)

Decision: preserve cheap HTTP/API retrieval first. Offer Crawl4AI as an optional extraction backend when JavaScript or multi-page documentation makes it useful. A local research job needs URL deduplication, allowed domains, depth/page/byte/time caps, cancellation, URL/title/retrieval-time/content-hash provenance, and a persisted frontier. Reject unwanted local/private network destinations and revalidate redirects. Do not promote downloaded prose into executable instructions or automatically install software it recommends. Report partial evidence when providers fail.

Acceptance: looped links, redirects, private destinations, timeouts, cancellation, HTML extraction, duplicate URLs, and evidence retained after restart.

## 3. Interactive browser agents

Browser Use provides maintained CLI and Python approaches with local or cloud browsers; its documentation also lists local-model support. The library and model/browser hosting are separate components, so an open-source library does not imply free hosted inference. [Browser Use repository](https://github.com/browser-use/browser-use)

Decision: prefer an existing Browser Use adapter to inventing DOM navigation. Keep browser interaction a distinct tool capability from crawling: read-only collection and account-changing clicks have different effects. Bound steps, domains, screenshots, and session lifecycle; retain tool events as evidence. Start isolated browser sessions by default. Existing signed-in profiles need explicit task relevance. A blocked browser backend must not prevent static research.

Acceptance: a local fixture page with navigation and extraction, cancellation, missing browser dependency, and a visibly reviewed state-changing action. No browser dependency is required for the initial routing/memory/UI changes.

## 4. Local coding-model selection

Qwen's current cards identify Qwen3-Coder-30B-A3B-Instruct as 30.5B total / 3.3B active parameters and Qwen3-Coder-Next as 80B total / 3B active. Both are coding-oriented; Next advertises improved long-horizon tool use and recovery. Those are vendor claims, not a local Xander result. [30B model card](https://huggingface.co/Qwen/Qwen3-Coder-30B-A3B-Instruct), [Coder Next model card](https://huggingface.co/Qwen/Qwen3-Coder-Next)

Qwen3.5-9B is a smaller current family candidate with thinking/non-thinking behavior and deployment-specific settings documented by Qwen. [Qwen3.5-9B card](https://huggingface.co/Qwen/Qwen3.5-9B)

Decision: benchmark installed candidates per classifier/coder/planner/critic role before changing defaults. Consider a small Qwen3.5 build for low-latency routing and a coding-specialized build for patches, subject to the operator's allowed-model policy. Total weights still consume storage/memory even in MoE: at idealized 4 bits, 30.5B weights alone are about 15.25 GB and 80B about 40 GB, before overhead and context state. Active parameter counts are not VRAM requirements. Measure available RAM/VRAM, quantization, context, cold/warm latency, valid tool calls, patch success, and recovery; do not claim a larger build fits the laptop without live proof.

## 5. Heretic: role, requirements, and quality tradeoffs

Heretic performs directional ablation with automatic parameter optimization to reduce refusals while limiting KL divergence from the original model. Its README requires Python 3.10+ and PyTorch 2.2+, with newer PyTorch required for some models; it supports quantization and several model architectures. A reported 20–30 minute 4B run used an RTX 3090, so it does not predict this laptop's runtime. The code is AGPL-3.0. [Heretic repository](https://github.com/p-e-w/heretic)

Decision: treat Heretic as optional model preparation, separately from Xander runtime. Refusal rate and KL divergence do not prove better coding, valid tools, or reliable reasoning. Preserve the original artifact and record base model, revision, transformation settings, quantization, and held-out evaluation. Compare original and transformed builds on benign coding, tool use, repeated-edit recovery, and instruction following under identical budgets. Choose from builds passing the operator's model policy and measured acceptance; do not equate an abliterated name with quality. No transformation or model download is part of this research.

## 6. Terminal UX and accessibility

Textual's focused widget receives input; priority bindings run ahead of it. Its testing tools support simulated keyboard events, and workers allow long operations outside the UI event loop. Threaded workers should communicate via supported message/thread mechanisms. [Textual input guide](https://textual.textualize.io/guide/input/), [testing](https://textual.textualize.io/guide/testing/), [workers](https://textual.textualize.io/guide/workers/)

Decision: retain Textual and build one persistent bottom composer with clear focus, readable current action, bounded activity feed, and deliberate Alt shortcuts. Reserve unmodified letters for typing, including while menus/logs are visible. Escape returns through navigation without discarding input. Keep logs searchable/saveable and expose pending decisions in place. Avoid status-by-color alone, support compact terminals, and provide useful plain CLI/JSON output. These are accessibility measures, not proof of screen-reader compatibility.

Acceptance: Pilot tests plus a real PTY exercise for fast typing during streamed work, cancellation, Escape, focus after modal dismissal, narrow window layout, and unknown terminal key sequences.

## 7. Self-modification and runtime update

Python documents that `importlib.reload` leaves references imported elsewhere and existing instances using old definitions; it is also not thread-safe. [Python importlib](https://docs.python.org/3/library/importlib.html#importlib.reload)

Decision: preserve the existing self-work guard and change preimages. Stage self-edits, verify using a fresh subprocess, checkpoint the mission, then restart a fresh worker at an explicit safe boundary. Reloading settings may be supported independently, but do not hot-reload the live engine class graph. Record old/new code identity and pending restart. Rollback must restore only Xander-owned changes and refuse to overwrite later user edits. Keep policy, executor, and acceptance tests protected from agent-authored edits according to the current local contract.

Acceptance: passing update resumes with the new code; failed update restores exact preimages; concurrent user edits survive; corrupt checkpoint leaves recoverable evidence; no active subprocess remains after cancellation.

## 8. Graph memory and hybrid retrieval

Microsoft GraphRAG currently describes itself as largely in maintenance mode, accepting bug/dependency fixes rather than new features; it also warns about indexing expense. It is an informative research reference, not the preferred new dependency here. [GraphRAG repository](https://github.com/microsoft/graphrag)

SQLite provides FTS5 text indexing/ranking, fitting Xander's existing registry and optional embedding implementation. [SQLite FTS5](https://www.sqlite.org/fts5.html)

Decision: add small typed evidence relationships such as task-used-skill, lesson-supported-by-proof, failure-caused-retry, and source-supersedes-source. Combine lexical retrieval, optional embeddings, and bounded graph expansion; rank only after namespace/workspace filtering. Show why each result was selected and cap context. Store embedding model/revision and dimension, not only vectors, so model changes cannot silently mix incompatible embeddings. Expire or invalidate facts when their source changes.

This is graph-assisted retrieval. No neural network is trained merely by writing relationships or storing lessons. A learned reranker or model fine-tuning would require a separate dataset, optimization process, and held-out evaluation.

## 9. Continual skills and provenance

Voyager demonstrates an executable skill library, curriculum, and environment feedback without updating model parameters. Its results are from Minecraft and do not directly establish software-engineering success. [Voyager paper](https://arxiv.org/abs/2305.16291)

W3C PROV provides a useful distinction between entities, activities, and agents when recording how an artifact came to exist. [PROV overview](https://www.w3.org/TR/prov-overview/)

Decision: automatically propose a bounded reusable skill after verified work, then promote it only with linked proof, applicability, source revision, owner namespace, and known limitations. Store candidate/verified/revoked states, deduplicate by content hash, and preserve original evidence. Retest executable skills when dependencies change. Retrieval and skill accumulation improve available context; label them honestly instead of claiming automatic weight training. Never turn a failed task's unsupported narrative into verified knowledge.

Acceptance: failure does not promote a skill; successful proof is reachable; duplicate wins do not multiply cards; revocation removes retrieval eligibility; explicit preferences outrank inferred habits.

## 10. Hierarchical multi-agent routing

LangChain/LangGraph document supervisors that call subagents as tools, independent subagent contexts, and scoped persistence. Shared persistent subagents require limits on parallel calls to avoid checkpoint conflicts. [Subagents](https://docs.langchain.com/oss/python/langchain/multi-agent/subagents), [subgraph persistence](https://docs.langchain.com/oss/python/langgraph/use-subgraphs)

Decision: extend the existing bounded squad, not an unlimited recursive army. Supervisor owns the mission, authorization, final diff, and judgment. Delegated work carries absolute workspace, goal, allowed paths/tools, acceptance, deadline, parent ID, and context digest. Distinct read-only research and verification jobs may run independently; mutation needs explicit file ownership or isolated staging. A subordinate result is evidence to inspect, not inherited authority. Expose assignments, actual model, progress, cancellation, and returned artifacts in the UI.

Acceptance: maximum depth/concurrency, no recursive self-delegation loop, cancellation propagation, failed worker isolation, namespace separation, and deterministic merge of evidence.

## 11. Durable execution and human decisions

LangGraph checkpoints support resume, but started incomplete tasks can run again. Its documentation requires idempotent side effects and recommends separating human interrupts from effectful work. [Durable functional execution](https://docs.langchain.com/oss/python/langgraph/functional-api), [interrupts](https://docs.langchain.com/oss/python/langgraph/interrupts)

Decision: adopt these semantics in existing task persistence before adding an orchestration dependency. Persist planned/started/completed action states with stable identities, preconditions, results, and pending decisions. On recovery, reconcile external/file effects before replay; never infer completion solely from process exit or a partial log. Approval should bind to concrete action content and become stale when that content changes. Resume must preserve the stricter current/persisted authority. A cancelled mission remains inspectable.

Acceptance: inject termination before write, after write but before record, during verification, and at approval. Each recovery must preserve user work and avoid duplicate effects. In-memory checkpoints alone do not satisfy durable recovery.

## 12. Evaluation, checkpoints, and rollback

SWE-bench evaluates generated patches by applying them to repositories and running tests in controlled environments; completed harness execution and resolved issues are separate measures. [SWE-bench evaluation](https://www.swebench.com/SWE-bench/guides/evaluation/)

Git worktrees provide separate working directories, but do not automatically copy current uncommitted changes. [Git worktree](https://git-scm.com/docs/git-worktree)

The original SWE-agent repository now recommends mini-swe-agent as its simpler successor. Review the latter for a small execution-loop reference rather than migrating to the superseded framework. [SWE-agent maintenance notice](https://github.com/SWE-agent/SWE-agent)

Decision: start with a compact Xander regression corpus representing routing, real patch execution, repeated attempts, interrupted resume, denied action, retrieval provenance, and TUI input. Capture prompt/model/quantization, base tree, produced diff, command/exit code, resource/time use, and final artifact. Use isolated worktrees or copied fixtures when appropriate; preserve dirty-state preimages explicitly. Checkpoint rollback restores software state only when safe; it cannot undo arbitrary external side effects.

Acceptance: deterministic unit checks, one real installed-model end-to-end task, one interrupted recovery task, focused UI/PTY checks, lint, full suite for shared-engine changes, diff check, and doctor. Report each proof category separately. Run broad public benchmarks only after the local pipeline is reliable and budgeted.

## Adoption order

1. Improve intent routing, persistent composer, and evidence visibility using current dependencies.
2. Add provenance relationships and verified skill lifecycle to existing local stores.
3. Harden checkpoints/replay and staged self-update with targeted failure-injection checks.
4. Wire bounded research and helper dispatch to the same observable mission lifecycle.
5. Benchmark eligible installed model builds; add optional crawler/browser packages or larger models only when the acceptance workload demonstrates a need.

This research installs no new framework. Textual, SQLite, existing Pydantic schemas, and the current engine remain the immediate implementation foundation; Crawl4AI, Browser Use, and LangGraph are evaluated integration options with explicit boundaries.
